The Architecture

What Single-Model Agents Get Wrong

Single-model coding agents are expensive and brittle. One model does planning, implementation, and self-review — the same model that produced the bugs in the first place. Context bloats. Costs explode. Quality is inconsistent because there is no true adversarial pressure.

OWA Coding Pattern is a deliberate upgrade: three different model families playing specialized roles in a tightly governed loop. Cheap, fast models do the heavy lifting in parallel. A strong independent critic (different training distribution, no social harmony) finds what the others miss. An orchestrator keeps the strategic thread and only declares victory when real tests pass and the adversary is satisfied.

The Core Loop

OWA Coding Pattern is a governed multi-agent system with explicit roles and exit criteria. It is not a free-form chat.

  1. Orchestrator (GPT-5.5) decomposes the task, defines acceptance criteria, and spawns workers.
  2. Workers (DeepSeek V4 Flash/Pro) implement scoped tasks in parallel and return diffs + test results.
  3. Adversary (Grok 4.3) performs a structured forensic review using HELD / STRAINED / BROKEN layers — invoked conditionally based on risk.
  4. Orchestrator decides whether to Accept, Refine (re-spawn workers for BROKEN items), or Reject (re-scope the task).
This is a governed process with explicit exit criteria. The Orchestrator is the sole decision maker. Workers execute. The Adversary critiques. Quality gates are enforced. OWA Coding Pattern only works because none of these models trust each other.
Model selection is your choice. GPT-5.5, DeepSeek V4, and Grok 4.3 are what the author uses — not a prescription. The pattern works with any capable models in each role. Substitute freely based on cost, latency, and what you trust.

Orchestrator alternatives: Claude Opus 4.8 (May 2026), Gemini 3.5 Flash (May 2026), Kimi K2.7 Code (June 2026).
Worker alternatives: Claude Sonnet 4.6, Qwen 3.6-Plus (April 2026), MiniMax M3 (June 2026), GLM-5.1 (April 2026).
Adversary alternatives: Claude Opus 4.8, Gemini 3.5 Flash with thinking. The key is picking a model from a different family than your orchestrator — the adversarial signal comes from independent reasoning, not raw capability.

Adversary Protocol & Decision Matrix

When to Invoke the Adversary

The adversary is the most expensive component. Use it only when the cost of shipping a defect is high:

ConditionInvoke?Max Budget
New module > 400 LOC or 4+ filesYes$4
Security, auth, payments, data pipelinesAlways$6
Refactor touching > 3 core modulesYes$3
Performance-critical hot pathYes$5
First implementation of new architectural patternYes$3
Simple feature < 150 LOC in one fileNo—
Bug fix with clear reproduction stepsNo—
Mechanical refactor or renameNo—
If any single condition triggers "Yes", the adversary runs. No exceptions for "it feels fine this time." The Orchestrator makes this call.

Grok Adversary Internal Council

The adversary operates as a council of specialized mental sub-agents that argue internally before producing a synthesized review:

  • @0day: Finds every way this can be exploited or fail under load.
  • @Architect: Hates God objects, tight coupling, future maintenance debt.
  • @Executioner: Obsessed with performance at 10x/100x scale.
  • @EdgeLord: Generates the most sadistic edge cases and contract violations.
  • @AppSec: Runs OWASP, auth, and attack surface analysis.

The adversary produces a decision artifact: findings triaged into KILL SHOTS (ship-blocking), FLESH WOUNDS (require mitigation before merge), and PAPER CUTS (non-blocking, logged). Each artifact carries a VERDICT score and a binding recommendation — Approve, Reject, or Major Surgery. The Orchestrator reads it and acts.

Adversary Output Protocol

Every adversary review must produce a structured artifact. The orchestrator is not allowed to proceed until this exists:

## Adversary Review — Round N
Task: [short description]
Files reviewed: [list]

HELD layers:
- Source / Requirements fidelity: ...
- Core logic & correctness: ...

STRAINED layers (with line refs):
- Edge cases & robustness: ...
- Maintainability & elegance: ...

BROKEN layers (MUST FIX):
- Security / attack surface: ...
- Efficiency / scaling: ...

Counter-Resonance flags (MUST STOP):
- Logic that will fail in production
- Security holes allowing escalation
- Design that cannot be tested or rolled back

Decision: ACCEPT | REWORK | REJECT
Recommended next action: ...

Loop Termination Criteria

The loop stops only when all three conditions are met:

  1. Adversary reports zero BROKEN items and ≤ 2 STRAINED items.
  2. Every STRAINED item has an explicit mitigation recorded.
  3. Orchestrator has re-run the full test suite (including any new tests the adversary required).
If the adversary still finds high-impact issues after round 3, the task is rejected and must be re-scoped. Do not let the loop run forever — cap at 3 iterations per task.

Setup & Configuration

Follow these steps exactly to enable the full OWA Coding Pattern. Full configuration lives in ~/.codex/config.toml and agent definition files in ~/.codex/agents/.

Step 1: Enable Multi-Agent Mode

[features]
multi_agent = true

[agents]
max_threads = 8 # parallel worker pool

Step 2: Add Model Providers

[model_providers.openrouter]
name = "OpenRouter"
base_url = "https://openrouter.ai/api/v1"
env_key = "OPENROUTER_API_KEY"
wire_api = "chat" # DeepSeek uses chat, not responses

[model_providers.xai]
name = "xAI"
base_url = "https://api.x.ai/v1"
env_key = "XAI_API_KEY"
wire_api = "chat"
Both DeepSeek and Grok require wire_api = "chat". Using "responses" will cause 401/400 authentication errors. This is the most common setup mistake.

Step 3: Create the DeepSeek Worker Agent

mkdir -p ~/.codex/agents
# ~/.codex/agents/deepseek_worker.toml

name = "deepseek-worker"
description = "Precise implementation worker. Minimal changes, high verification."
model_provider = "openrouter"
model = "deepseek/deepseek-v4-flash"
temperature = 0.25
max_tokens = 32768

developer_instructions = """
[full soul prompt as shown in Souls section above]
"""

Step 4: Create the Grok Adversary Agent

# ~/.codex/agents/grok_adversary.toml

name = "grok-adversary"
description = "Ruthless adversarial critic. Finds structural, security, and correctness issues."
model_provider = "xai"
model = "grok-4.3"
temperature = 0.0 # deterministic — no creativity on critique
max_tokens = 16384
model_reasoning_effort = "high"

developer_instructions = """
[full adversary soul as shown in Souls section above]
"""

Step 5: Register the Agents

[agents.deepseek_worker]
description = "Fast coding executor on DeepSeek V4 Flash"
config_file = "~/.codex/agents/deepseek_worker.toml"

[agents.grok_adversary]
description = "Independent critic on Grok 4.3"
config_file = "~/.codex/agents/grok_adversary.toml"

Step 6: Set Environment Variables

# ~/.zshrc (or your shell profile)

# Codex Orchestrator — already set
export OPENAI_API_KEY="sk-..."

# DeepSeek Worker via OpenRouter
export OPENROUTER_API_KEY="sk-or-v1-..."

# Grok Adversary
export XAI_API_KEY="xai-..."

After editing, run source ~/.zshrc and restart Codex. If Codex CLI or its sub-agents can't see these variables, agent spawns fail with 401 errors.

Grok 4.3 through xAI's direct API has different pricing than through OpenRouter. If you have SuperGrok/API credits, the xAI direct endpoint is cheaper. Check your xAI billing before running the adversary at scale.

Step 7: Enable Multi Agents in Codex

Launch Codex CLI and run:

/experimental

Enable Multi Agents when prompted.

Step 8: Verify

# Verify Codex CLI
codex --version # should return v26.x+

# Verify environment
echo $OPENAI_API_KEY
echo $OPENROUTER_API_KEY
echo $XAI_API_KEY

Usage & Workflows

Basic Worker Spawn

Inside a Codex CLI session, tell the orchestrator what you want:

# Spawn a single worker
"Spawn a deepseek_worker to implement the user authentication module in src/auth/. Include tests."

# Parallel workers for multi-file feature
"Spawn 2 deepseek_worker for the backend routes and 1 for the payment processing logic."

# Worker + adversary review
"Spawn a deepseek_worker for the payment flow. When done, decide if a grok_adversary review is needed."

# Full OWA Coding Pattern
"This is a large task. Use orchestrator mode. Break it into modules. Spawn workers for each
module, then run the adversary on the integrated result before declaring done."

Pitfalls & Sharp Edges

Wire API mismatch: DeepSeek and Grok both use chat format. If a provider silently requires responses, calls fail with 401/400. Test with a single spawn before relying on it.
Sub-agents have zero memory of the orchestrator conversation. Every spawn must contain all file paths, constraints, and acceptance criteria in the prompt itself. There is no shared context window.
OpenRouter rate limits under parallel spawns. At 8 concurrent workers, you may hit tier-based throttling. OpenRouter's paid tiers give higher concurrency. If you see 429s, reduce max_threads.
Cost guardrails: Default adversary budget per task is $3–5. Anything over $6 requires explicit approval. Log every invocation with (task ID, round number, tokens, cost, final decision).
Never run the adversary on tasks below the threshold — it becomes expensive theater. Simple features, bug fixes with clear reproduction, and mechanical refactors don't need it.
After setup, test with a small task first before using the adversary on large work. Verify the full loop works end to end with a trivial module before trusting it on production code.
